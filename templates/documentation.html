1. The 4 Necessary Coffman Conditions

A deadlock situation can arise if and only if the following four conditions hold simultaneously in a system:

1. Mutual Exclusion

At least one resource must be held in a non-shareable mode; only one process at a time can use the resource.

2. Hold and Wait

A process must be holding at least one resource and simultaneously waiting to acquire additional resources held by others.

3. No Preemption

Resources cannot be forcibly taken away; they can only be released voluntarily by the process holding them after completion.

4. Circular Wait

A set of waiting processes {P0, P1, ..., Pn} exists such that P0 waits for P1, P1 waits for P2, and Pn waits for P0.

2. Prevention vs Avoidance vs Detection vs Recovery

Strategy Core Concept Knowledge Required Trade-off
Deadlock Prevention Invalidates at least one of the 4 Coffman conditions at design time. Resource ordering or lock policies. Low resource utilization and possible starvation.
Deadlock Avoidance Dynamically assesses request safety before granting (Banker's Algorithm). Prior knowledge of maximum claims (Max matrix). Processes must declare future resource demand in advance.
Deadlock Detection Allows requests freely; periodically examines state for existing deadlocks. Current Allocation and active Request vectors only. Runtime overhead of cycle/detection searches.
Deadlock Recovery Resolves an existing deadlock via process termination or preemption. Victim selection heuristic (cost, priority). Work loss from terminated processes or rollback complexity.

3. Banker's Algorithm (Safety Algorithm)

Devised by Edsger Dijkstra, the Safety Algorithm determines whether a system is in a safe state:

1. Let Work = Available, and Finish[i] = false for i = 0, 1, ..., n-1.
2. Find an index i such that both:
   a. Finish[i] == false
   b. Need[i] ≤ Work
   If no such i exists, go to step 4.
3. Work = Work + Allocation[i]
   Finish[i] = true
   Append P_i to safe sequence, then return to step 2.
4. If Finish[i] == true for all i, then the system is in a SAFE STATE.

4. Banker's Resource-Request Algorithm

When process Pi makes a request vector Request[i]:

  1. Step 1: If Request[i] ≤ Need[i], proceed to Step 2. Otherwise, raise error (process exceeded maximum claim).
  2. Step 2: If Request[i] ≤ Available, proceed to Step 3. Otherwise, Pi must wait (insufficient resources available).
  3. Step 3: Pretend to allocate requested resources to Pi: 
    Available = Available - Request[i]
Allocation[i] = Allocation[i] + Request[i]
Need[i] = Need[i] - Request[i]
  4. Step 4: Run Safety Algorithm on tentative state.
  5. Step 5: If SAFE → commit allocation. If UNSAFE → rollback tentative state, restore previous state, and Pi waits.

5. Deadlock Detection Algorithm (Multi-Instance)

Employed when processes do not declare maximum demand. Uses current Available, Allocation, and active Request vectors:

1. Work = Available
2. For i = 0 to n-1:
   If Allocation[i] ≠ 0, Finish[i] = false; else Finish[i] = true.
3. Find index i such that:
   Finish[i] == false AND Request[i] ≤ Work
   If found: Work = Work + Allocation[i]; Finish[i] = true; repeat step 3.
4. If Finish[i] == false for any i, the system is in DEADLOCK, and process P_i is deadlocked.

6. Resource Allocation Graph (RAG) vs Wait-For Graph (WFG)

Resource Allocation Graph (RAG)
  • Process nodes (circles) and Resource nodes (rectangles).
  • Directed edge Rj → Pi: Assignment / Allocation edge.
  • Directed edge Pi → Rj: Request edge.
  • Cycle in single-unit resources implies guaranteed deadlock. In multi-unit resources, cycle is necessary but not sufficient.
Wait-For Graph (WFG)
  • Only Process nodes (Pi).
  • Directed edge Pi → Pj indicates Pi is waiting for a resource held by Pj.
  • Obtained by collapsing resource nodes from the RAG.
  • Cycle in single-unit WFG guarantees deadlock.
